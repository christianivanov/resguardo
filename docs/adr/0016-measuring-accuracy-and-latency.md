# 0016. Measuring accuracy and latency

- **Status:** Accepted
- **Date:** 2026-11-26

## Context

Milestone M6 publishes two numbers that the README promises:
- the false-positive rate of the detectors, measured on a Spanish corpus;
- the latency Resguardo adds.

The design document asks for about 300 synthetic Spanish texts that look sensitive and are not, about 100 that are sensitive in format, a CI check that fails if false positives rise, and a benchmark "with `criterion`". `criterion` would be a new dependency. Open points: how the corpus is built and labelled, what counts as a false positive, how the CI check knows the published numbers, and how latency is measured.

## Decision

1. **Corpus:** `fixtures/accuracy/corpus.jsonl`, committed.
   - Each line has the `text`, the classes it must `expect`, the classes it may `allow` without that being a mistake, and a `group`.
   - It is generated by `tools/accuracy/generate.py` with a fixed seed, and every value is invented.
   - The generator computes check digits (DNI, NIE, CIF, IBAN, Luhn) on its own, so the corpus tests the Rust detectors instead of repeating them.
   - It includes the examples of Annex G.6, values with a wrong check digit, and known gaps on purpose.
2. **Counting.** Per class:
   - a **miss** is an expected class not found;
   - a **false positive** is a class found that was neither expected nor allowed.

   The false-positive rate is over the negatives, the texts that expect nothing. `secret_candidate` is allowed on commit hashes, UUIDs and tracking numbers (Annex G.6).
3. **Gate.**
   - `resguardo accuracy --baseline fixtures/accuracy/baseline.json` exits with 1 (ADR 0009) if any class has more misses or more false positives than the baseline.
   - The baseline holds the counts published in `docs/ACCURACY.md`. The check is run locally (`cargo run -p resguardo -- accuracy --baseline fixtures/accuracy/baseline.json`); the project uses no hosted CI.
   - Updating the baseline is a deliberate change, made in the same commit as the detector change and the document.
4. **Benchmark without `criterion`.** `tools/bench` is a binary in the workspace that uses only existing dependencies.
   - It times scanning on texts of 1, 16 and 256 KB.
   - It sends the same 400 sequential requests straight to the mock and through an in-process Resguardo, with `fsync` on and off and with a redaction, and reports p50, p95 and p99 and the difference.
   - This gives the "added latency" the README promises. Statistical rigour, outlier handling and regression tracking are what `criterion` would add, for micro-benchmarks that v0.1 does not need.
5. **Outcome entries without `fsync`.** The first measurement showed two flushes per request, which doubled the added latency. Only the decision entry must be on disk before the request leaves, so outcomes no longer wait for their own flush (ADR 0015).

## Consequences

- Both numbers can be reproduced with one command each, and the documents state the machine they were measured on.
- The corpus is synthetic. It catches regressions and gives an honest order of magnitude, not a promise for any particular workload.
- Without `criterion`, small performance regressions are not caught automatically. The benchmark is run by hand before a release.
